# Hands-free Background Voice Chat Implementation Plan

**Goal:** Add a user-started, half-duplex voice-call mode that endpoints speech, sends the finished utterance automatically, speaks the completed reply, and listens for the next turn while the app is backgrounded or the screen is locked.

**Architecture:** A local Expo module owns the native microphone/audio session and Android foreground service for the lifetime of a call. A root React provider runs a deterministic turn state machine and sends recognized text through the existing `sendChatInput` path; the Gate and every backend remain unchanged. Push-to-talk continues to use `expo-speech-recognition` -> composer draft -> explicit Send, and ordinary optional playback continues to use `expo-speech`.

**Tech stack:** Expo SDK 57 / React Native 0.86, Expo Modules API, Android `SpeechRecognizer` + `TextToSpeech` + microphone/media-playback foreground service, iOS `SFSpeechRecognizer` + `AVAudioEngine` + `AVSpeechSynthesizer`, existing Gateway context and Jest suite.

**Spec:** `FUTURE-ITEMS.md`, “Hands-free background voice chat” and “Solution B — Voice chat capability (B1–B3 SHIPPED)”.

## Decision

Choose **(a) client-side turn-taking**.

It is the only route that immediately covers every connected Hermes, OpenCode, Codex, and Claude Code profile through the same existing text-chat contract. Audio stays on the operator’s phone; only the recognized text and the existing text response cross the already-paired connection. The app gains no model credential, the Gate gains no provider credential or audio broker, and there is no paid realtime-provider dependency.

This is deliberately a **half-duplex call**, not Solution B4. While the operator is speaking, reply playback is stopped; while the reply is streaming or being spoken, full recognition is not producing a user turn. The implementation forfeits B4's low-latency audio-to-audio stream, provider-side semantic endpointing, and continuous simultaneous listen-while-speaking. Those losses are accepted for the backend coverage, credential posture, and smaller Gate-free scope.

**Revised 2026-09-12 against current industry practice.** OpenAI's July 2026 "GPT-Live" is genuinely full-duplex — it listens and speaks at once and can murmur backchannel acknowledgments while the user is still talking. That is not being matched here; it requires continuous bidirectional audio streaming and is exactly what B4 (and now more than B4 originally scoped) would take. What *is* in reach without that architecture, and folded into the steps below: **interrupt-by-speaking**. Google's own Gemini Live API does not pause its TTS server-side either — the documented integration pattern is client-side voice-activity detection that stops playback locally. That is the same shape of fix applied here: a lightweight on-device VAD listens during `speaking` (reusing the communication-mode audio session Step 2/3 already configure for echo cancellation) and an interrupt hands control back to listening immediately. It recovers "just start talking to interrupt," not simultaneous listen-and-speak or verbal backchanneling — the plan must not describe it as full-duplex or as parity with GPT-Live.

The call path deliberately diverges from B1’s “never auto-send” composer rule. The modes are visibly and structurally separate:

- The existing microphone remains **Hold to dictate**. Its transcript continues to land in the composer for review and never sends.
- A separate phone control is **Start hands-free call**. Before the first call, a sheet says “Speech is sent automatically when you pause” and requires an explicit **Start call** tap.
- During a call, a persistent banner says **Hands-free call · speech auto-sends** and exposes Mute, Skip reply, and End. Call transcripts never pass through the composer writer.
- Ending the call restores the untouched typed draft. Any recognized text that was not accepted by the connected send path is recovered into that draft for review, never queued for later automatic delivery.

## Seamlessness pass (2026-09-12, informed by current voice-assistant practice)

Four additions to the steps below, made after checking current documented
behavior of the major voice assistants rather than assuming it. None of them
reopen the (a)/(b) decision above or add a backend/provider dependency — each
is a client-side addition to the architecture already chosen.

1. **Interrupt-by-speaking (barge-in via on-device VAD).** Documented as the
   standard integration pattern for exactly this situation: Google's own
   Gemini Live API does not pause TTS server-side when the user speaks —
   the API documentation directs client integrators to implement client-side
   audio mixing or silence detection to suppress agent audio. That is what is
   added here: a lightweight voice-activity listener, active only during
   `speaking`, reusing the communication-mode audio session Steps 2–3 already
   configure (which already does hardware/software echo cancellation for this
   exact reason). It does not run full recognition and does not transcribe —
   it only detects that the user started talking, stops playback, and hands
   off to a real listening turn. See Step 3 (`bargeIn` event) and Step 4
   (`speaking -> listening` on `bargeIn`).
2. **A grace window before a silence-triggered send.** OpenAI's original
   turn-based Advanced Voice Mode's most-cited failure was exactly this: it
   detected the user's turn by listening for silence, so a pause to think
   was frequently mistaken for "done talking" and the model barged in with an
   unwanted answer. This plan's fixed silence thresholds (Step 3) are exposed
   to the identical failure mode. Rather than guess at different fixed
   milliseconds without device data, Step 4 adds a short client-side grace
   hold after a silence-triggered `final`: if the user resumes speaking before
   the hold elapses, the pending send is cancelled and the utterance
   continues. This is a pure state-machine change, consistent with the
   existing reducer's tested handling of duplicate/late native events.
3. **Progressive sentence-level speech.** Well-established latency technique
   (search results below cite the general "speak while the model is still
   generating" pattern, sometimes called LLM2Speech): synthesizing and
   playing audio for a completed sentence while later sentences are still
   streaming in, rather than waiting for the full reply to finish. B2 already
   implements sentence-boundary chunking for ordinary playback
   (`Speech.maxSpeechInputLength`) — Step 6 reuses that exact chunking during
   a call instead of the full-message wait it currently requires.
4. **Ambient state feedback instead of banner text alone.** Both major voice
   assistants use a continuously animated, audio-reactive visual (a
   pulsing orb/waveform) rather than a static status label, because it signals
   "it is listening to you right now" far more convincingly than text. Step 7
   adds a lightweight amplitude-driven animation using the Skia dependency
   already in this repo, plus a short non-verbal earcon the instant a send is
   dispatched — an honest analog to GPT-Live's verbal backchannel murmurs
   ("mmhm" while you talk), which cannot be reproduced here without either
   fabricating speech the model never produced or true full-duplex audio.

**What remains forfeited even after this pass**, stated plainly so it is never
mistaken for parity: continuous simultaneous listen-while-speaking, verbal
backchanneling while the user talks, and provider-side semantic
understanding of *when* a thought is actually finished. Those require true
full-duplex audio streaming — Solution B4 or beyond — and are out of scope
here for the same credential/cost reasons the Decision section already gives.

Sources consulted: [I Talked to ChatGPT's GPT-Live for a Week](https://medium.com/@ffguci8/i-talked-to-chatgpts-gpt-live-for-a-week-here-s-why-it-changes-everything-0f89ade4d3c6), [ChatGPT Voice vs Grok vs Gemini Live (2026)](https://tech-insider.org/chatgpt-voice-vs-grok-voice-vs-gemini-live-2026/), [Speak While You Think: Streaming Speech Synthesis During Text Generation](https://arxiv.org/pdf/2309.11210).

## Global constraints and compatibility facts

- B5 remains absolute: there is no wake word, boot receiver, background start, or automatic resume. Android starts its microphone service only from the visible Start-call tap; both platforms stop on End, system interruption, disconnect, or process death.
- No code may branch on `hermes`, `opencode`, `codex`, or `claude-code`. Call availability is the conjunction of a connected text-chat surface and advertised/on-device audio readiness. No `realtime-voice` capability is required or invented.
- `expo-speech-recognition@57.0.0` and `expo-speech@57.0.2` remain installed for B1–B3 and are not refactored into the call runtime. Their foreground behavior is shipped; their sustained background behavior is not documented, so the call does not assume it.
- Do not add `expo-audio` as a keepalive. The [SDK 57 audio docs](https://docs.expo.dev/versions/v57.0.0/sdk/audio/) confirm its background service belongs to its own recorder/player; running a second recorder beside speech recognition would contend for the microphone. The local module uses the SDK 57 Expo Modules API and the platform speech/audio APIs directly.
- Exact native configuration is locked. Android declares `RECORD_AUDIO`, `POST_NOTIFICATIONS`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MICROPHONE`, and `FOREGROUND_SERVICE_MEDIA_PLAYBACK`, plus a non-exported service with `android:foregroundServiceType="microphone|mediaPlayback"` and `android:stopWithTask="true"`. iOS declares `UIBackgroundModes = ["audio"]` and keeps the existing `NSMicrophoneUsageDescription` and `NSSpeechRecognitionUsageDescription` strings accurate for both dictation and calls.
- Do not use Android’s `phoneCall` foreground-service type, Telecom/ConnectionService, or iOS CallKit: this is a model conversation, not a carrier/VoIP peer call. Use a microphone/media-playback service and an ordinary ongoing notification.
- The device acceptance gate in Final verification items 3–8 is mandatory. Expo Modules API compatibility with SDK 57 is documented, but native background recognition across OEMs is not confirmed until the physical-device matrix passes. A failure blocks release; it must not be relabeled as a foreground-only success.

### 3. Implement native recognition, endpointing, and reply speech

**Files:** modify `modules/handsfree-voice/expo-module.config.json`, `modules/handsfree-voice/ios/HandsfreeVoice.podspec`, `modules/handsfree-voice/android/src/main/java/com/versutus/handsfreevoice/HandsfreeCallService.kt`, `modules/handsfree-voice/android/src/main/java/com/versutus/handsfreevoice/HandsfreeVoiceModule.kt`; create `modules/handsfree-voice/android/src/main/java/com/versutus/handsfreevoice/HandsfreeEndpointing.kt`, `modules/handsfree-voice/android/src/test/java/com/versutus/handsfreevoice/HandsfreeEndpointingTest.kt`, `modules/handsfree-voice/ios/HandsfreeVoiceModule.swift`, `modules/handsfree-voice/ios/HandsfreeVoiceAppDelegateSubscriber.swift`, `modules/handsfree-voice/ios/HandsfreeEndpointing.swift`, `modules/handsfree-voice/ios/Tests/HandsfreeEndpointingTests.swift`, `__tests__/handsfree-native-contract-test.ts`.

- [ ] Android: own one main-thread `SpeechRecognizer` per listening turn with partial results. Set complete silence to 900 ms, possibly-complete silence to 600 ms, minimum speech to 300 ms, and a 60-second utterance ceiling. `onResults` emits one trimmed `final`; silence with no words emits `noSpeech`; recoverable recognizer endings restart only while the same user-started session remains active.
- [ ] iOS: configure `AVAudioSession` as `.playAndRecord`, mode `.voiceChat`, options `.defaultToSpeaker` and `.allowBluetooth`, then keep `AVAudioEngine` active for the call’s lifetime. Feed samples to `SFSpeechAudioBufferRecognitionRequest` only in `listening`; while waiting/speaking, discard them without recognition or persistence so the audio background mode remains legitimate but ambient audio is not retained.
- [ ] iOS endpointing: after speech crosses the adaptive noise floor, 900 ms below it finishes the recognition task; 10 seconds with no speech emits `noSpeech`; 60 seconds caps an utterance. Emit the best trimmed transcription once. No audio file is written on either platform.
- [ ] Native TTS: queue the supplied `speechChunks` in order through `TextToSpeech` / `AVSpeechSynthesizer`, applying the existing Bot voice identifier, rate, and pitch. Stop recognition before speech to prevent echo; emit `speechFinished` only after the last chunk. `stopSpeaking` must flush the queue and never emit a stale completion.
- [ ] **Barge-in VAD (seamlessness pass, item 1):** while `speaking`, run a lightweight energy-based voice-activity listener on the same communication-mode audio session already active for echo cancellation — this does not run `SpeechRecognizer`/`SFSpeechRecognizer` and produces no transcript. On Android, an `AudioRecord` tap or the recognizer's own RMS callback is sufficient; on iOS, an `AVAudioEngine` input tap computing short-window RMS. Voice crossing the ambient noise floor for a continuous ~250 ms emits `bargeIn` exactly once, then the listener stops itself until the next `speaking` phase. On `bargeIn`, immediately flush the TTS queue (the same path `stopSpeaking` uses) and stop — do not wait for `speechFinished`. This does not transcribe the interrupting speech; JS starts a fresh `startListening()` in response, and normal endpointing captures what the user says.
- [ ] **Amplitude event (seamlessness pass, item 4):** during `listening` and `speaking`, emit `level` (0–1) at a modest rate (~10/s) from whichever audio tap is already open for recognition or barge-in detection. This is best-effort UI polish, not a correctness signal — a platform that cannot supply it cheaply may omit it, and JS must render a static (non-animated) state rather than fail when it is absent.
- [ ] Observe `AVAudioSession.interruptionNotification`; on `.began`, emit `interruption` and tear down. The AppDelegate subscriber performs the same idempotent cleanup on termination; register it in `expo-module.config.json` and add the endpointing XCTest target to the podspec. Route/headset loss is fatal to the call rather than silently switching microphones.

### 4. Add the pure call state machine and crash-safe draft recovery

**Files:** create `src/lib/voice/handsfree-session.ts`, `src/lib/voice/handsfree-recovery.ts`, `__tests__/handsfree-session-test.ts`, `__tests__/handsfree-recovery-test.ts`; modify `src/lib/gateway/composer-draft.ts`, `__tests__/composer-draft-test.ts`.

- [ ] Define `HandsfreePhase = 'idle'|'starting'|'listening'|'confirming'|'sending'|'waiting'|'speaking'|'muted'|'ending'|'ended'` and terminal reasons `user|disconnect|system-interruption|app-killed|thread-changed|recognition-failed|send-failed|speech-failed` in the pure reducer `reduceHandsfreeSession`.
- [ ] Lock the cycle: `listening -> confirming` on one non-empty final transcript (never straight to `sending` — see the grace-window bullet below); `confirming -> sending` only once the grace window elapses with no further speech; `sending -> waiting` only on send outcome `sent`; `waiting -> speaking` only on the correlated assistant message (streaming or completed — Step 6 speaks progressively); `speaking -> listening` on native `speechFinished` **or** `bargeIn`; Mute stops recognition, and unmute returns to listening.
- [ ] **Grace window before send (seamlessness pass, item 2):** on entering `confirming`, start a short timer (default 600 ms — a first pass, expected to need the same on-device tuning as the native silence thresholds; do not treat it as final without the device matrix in Final verification). If native emits a new `partial` or `final` before the timer fires, cancel the pending send, concatenate the new transcript onto the held text (recognizer results in this window are independent utterances chunked by the recognizer's own silence cutoff, not one continuous stream — concatenation is the correct join), restart the timer, and return to `confirming`. Only once the timer elapses with nothing pending does `sendChatInput` fire with the fully accumulated text. This exists because fixed-duration silence endpointing is a documented, specific failure mode of exactly this kind of system — it is what caused OpenAI's original turn-based Advanced Voice Mode to interrupt users mid-thought before GPT-Live replaced it with full-duplex audio. This grace window is the client-side mitigation available without that architecture.
- [ ] Persist the latest partial/final under `handsfree-recovery:<composerDraftKey>` on every transcript event. Clear it only after `sendChatInput` accepts the turn as `sent`. On any terminal path or next launch, merge a stale recovery into the ordinary composer with `spokenDraftText`, then remove the recovery record.
- [ ] Keep recovery text out of `spokenDraftHold`: call transcripts have their own writer and never invoke the B1 hold callbacks. Preserve an existing typed draft byte-for-byte until recovery is actually needed.

**Verify:** Jest covers every transition, duplicate/late native events, empty finals, mute/unmute, send failure, process-restart recovery, recovery merged after existing draft text, and clearing only after `sent`. Plus: a resumed utterance within the grace window cancels the pending send and concatenates correctly; the timer firing with nothing pending sends exactly the accumulated text; a `bargeIn` during `speaking` transitions to `listening` and never fires the `speechFinished` cleanup twice; `confirming` is included in every place the reducer's existing tests already assert phase invariants (e.g. no legal path skips it between `listening` and `sending`).

## Call termination and failure behavior

- **Normal End:** UI or Android notification End immediately stops recognition/TTS, deactivates the audio session/foreground service, releases audio focus, promotes unsent recovery to the composer, and never restarts.
- **Gateway disconnect:** end with `disconnect`; never put a final into the offline outbox. Already accepted user turns remain in chat. A reply that completes remotely is loaded normally on reconnect but is not spoken by a dead call.
- **Incoming phone/VoIP call:** iOS audio-session interruption or Android audio-focus loss ends the Versutus call, releases the mic/speaker, and requires a fresh visible Start after the system call. It does not auto-resume listening.
- **App kill/task swipe/OS process death:** Android’s `stopWithTask=true`, `onTaskRemoved`, and `START_NOT_STICKY` remove the service/notification; iOS process death ends its audio session. No boot or relaunch path resumes. The latest JS-delivered partial is recovered into the composer on next launch; audio after that persisted partial is honestly unrecoverable because audio is never recorded.
- **Recognition/TTS fatal error or headset route loss:** stop the call, surface the native reason in the banner on return, and recover unsent text. Recoverable no-speech is not fatal and sends nothing.
